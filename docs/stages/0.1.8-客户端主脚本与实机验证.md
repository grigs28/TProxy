## 🔴 实机验证暴露了 4 个真实缺陷（服务端自测全都发现不了）

这 4 个问题的共同点：**在服务端本机测试全部通过，只有真实客户端会暴露**。

### 1. tengine 缺 CA 分发端点

客户端下载根 CA 时报 `curl: (52) Empty reply from server`。
原因：客户端访问的是 **IP**（`Host: 192.168.0.18`），不匹配任何 `server_name`，
落入 `default_server` 而被 `return 444` 拒掉。
修复：在 `default_server` 加 `location = /tproxy-ca.crt` 并挂载 CA 文件。

### 2. 宿主 `/etc/hosts` 静默压过劫持

`github.com` 解析到真实 IP，而其他域名全部正常。dnsmasq 日志点破：

```
github.com:  /etc/hosts github.com is 20.205.243.166    ← 来自 hosts
gitlab.com:  config gitlab.com is 192.168.0.18          ← 来自 address=
```

dnsmasq 读宿主 hosts（host 网络），且 **hosts 记录优先级高于 `address=`**。
宿主里旧的手工 github 记录把劫持压住了。
修复：备份后移除这些记录。

### 3. firewalld 未放行 443

```
connect to 192.168.0.18 port 443 failed: No route to host
```

firewalld 开放了 `80/tcp`、`53`、`4999-5010` 等，**唯独没有 443**，
而 nginx 确实在监听。表现为「服务端自测全绿、客户端完全连不上」。
修复：`deploy.sh` 显式放行 443/tcp 80/tcp 53/tcp 53/udp。

### 4. conda 的 curl 不读系统信任库

`curl` 报 `unknown CA`，但 `/usr/bin/curl` 完全正常：

```
*  CAfile: /opt/conda3/ssl/cacert.pem      ← conda 自带 CA bundle
```

该机的 `curl` 来自 conda，用 conda 的 CA 文件，系统装的根 CA 对它无效。
**极具迷惑性**：同一台机器上两个 curl 行为相反。
修复：新增 `install_runtime_ca()` 处理自带 CA bundle 的运行时。

### 由此新增：配置体检脚本

把上述陷阱固化为 `proxy/tests/preflight.sh`：监听端口 / 防火墙 / hosts 冲突 /
劫持生效 / 容器健康 / 证书覆盖，在跑测试**之前**运行。
