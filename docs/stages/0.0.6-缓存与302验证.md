# 0.0.6 — 缓存行为与 302 跳转验证

**提交**：`744e78c`
**计划**：[Task 6](../plans/2026-09-23-phaseA-core-proxy.md)

## 目标

端到端验证缓存命中、TTL 分级，以及最关键的——**上游 302 跳转不会让客户端绕过代理**。

## 产出

| 文件 | 职责 |
|---|---|
| `proxy/tests/test-cache.sh` | 缓存命中、302 跟随、落盘验证 |

## 背景：为什么 302 是这套方案的命门

实测 `repo.openeuler.org` 会返回 302 跳转到 `dl-cdn.openeuler.openatom.cn`：

```
https://repo.openeuler.org/openEuler-24.03-LTS-SP3/OS/x86_64/repodata/repomd.xml
  → HTTP 302
  → location: https://dl-cdn.openeuler.openatom.cn/...
  → HTTP 200, 3566 bytes
```

若只劫持 `repo.openeuler.org` 而不管跳转目标，客户端会去请求
`dl-cdn.openeuler.openatom.cn` —— 那个域名没被劫持，**直接走公网，缓存完全失效**。

本方案的应对是双重的：dnsmasq 劫持链上全部域名 + tengine `proxy_redirect off`
让 302 原样透传（客户端再次打到本机）。

## 验证证据

```
$ ./proxy/tests/test-cache.sh
== 清空缓存，确保测试可重复 ==
  已清空
== 首次请求应为 MISS ==
  -> MISS
== 二次请求应为 HIT ==
  -> HIT
== 跟随 302 后应拿到合法 XML（证明跳转未出内网）==
  ✅ 返回合法 XML
== 缓存目录应有实际文件 ==
  ✅ 缓存文件数: 2
CACHE-ALL-PASS
```

测试对 `repo.openeuler.org` **和** `dl-cdn.openeuler.openatom.cn` 都做了
`--resolve` 指向代理 —— 否则 curl 会直连公网，测试本身就绕过了代理，
成了假绿。

## 遗留

**跳转目标变更风险** — 若上游日后改跳到未知第三方域名，劫持清单不会覆盖它，
缓存会被绕过。`proxy_redirect off` 的策略依赖「跳转目标可枚举」这一前提，
需在运维中留意（计划 B/C 可考虑加监控）。
