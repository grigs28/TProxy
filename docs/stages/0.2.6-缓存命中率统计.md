# 0.2.6 — 缓存命中率统计

**提交**：`44ca75b`
**性质**：计划 D 的补充实现（spec §3.1 列为「核心」但首版未做）

## 目标

回答「缓存到底有没有在起作用」。

这是本项目最初的痛点：旧系统里 7 个 registry 崩溃 1.7 万次、缓存长期为零，
却因为**看不见**而无人察觉。占用统计只能说明「存了多少」，命中率才说明
「是否真的避免了回源」。

|---|---|
| `manager/backend/hitrate.py` | 解析 nginx 日志统计命中率 |
| `manager/tests/test_hitrate.py` | 7 项测试 |
| `manager/app.py` | 新增 `/api/hitrate` |
| `manager/static/app.js` | 命中率区块 |

## 三个关键判定

### 1. 解析必须对照实际 `log_format`

真实的日志行尾是 `cache=HIT`：

```
127.0.0.1 - [23/Sep/2026:05:09:28 +0000] "GET / HTTP/1.1" 200 696 "-" "curl/8.4.0" cache=HIT
```

**这正是旧 proxy-manager 的 monitor 翻车处** —— 它期望 `cache_status="HIT"`，
与实际格式不符，于是匹配不到任何行、界面恒为空却不报错，故障因此持续数月。
故本次先实测日志格式再写正则，测试样例也全部按真实格式书写。

### 2. `STALE` / `UPDATING` 必须计入命中

| 状态 | 归属 | 理由 |
|---|---|---|
| `HIT` / `STALE` / `UPDATING` | **命中** | 都由缓存提供了响应——STALE 是返回过期副本并后台刷新，UPDATING 是刷新中仍以副本应答 |
| `MISS` / `BYPASS` / `EXPIRED` | 未命中 | 真正回源取全量 |

排除 STALE/UPDATING 会**系统性低估**命中率，而这两种状态恰恰出现在
「缓存正被有效使用」的时刻（元数据 TTL 只有 5–10 分钟，过期刷新很常见）。

### 3. `cache=` 为空是「不适用」而非未命中

`registry` 与 `git` 在 tengine 中配的是 `proxy_cache off`，缓存由各自后端管理，
日志里没有命中标记。实测这两个日志的 `cache=` **全部为空**。

把它们算作未命中会得出 0% 的荒谬结论；界面改为标注「后端自缓存」。


生产机实测：

```
$ ./tests/test-manager.sh
  ✅ 命中率: os=49.2% python=70.2% nodejs=75.8% java=92.0%
MANAGER-ALL-PASS
```

## 执行中的一个自省

第一版测试断言写成 `grep '"rate": [0-9]'`（**带空格**），而 `jsonify` 输出的是
紧凑格式 `"rate":49.2` —— 断言把完全正常的 API 判成了故障。

**教训**：写断言时也要先看真实输出，不能凭对格式的假设。这与 0.1.x 系列
「测试通过 ≠ 验证了那件事」是同一类问题。

## 遗留

- 命中率基于日志尾部采样（默认 20000 行），非全量统计
- 无历史趋势（未引入持久化）
