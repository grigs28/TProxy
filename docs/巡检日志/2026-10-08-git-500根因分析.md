# git 「错误的行长度字符串：500」根因分析

> 2026-10-08 · 只读研究，未修改任何程序/配置
> 起因：本机 git fetch 报 `错误的行长度字符串：500`，直连真实 GitHub IP
> （140.82.116.4）正常。用户给出的假设：DNS 劫持到 .18 后，
> GET 能应答、POST 协商返回异常 → git 把错误内容当成 pkt-line 长度前缀。

## TL;DR

**用户的假设方向正确，机制已实测钉死**，但有两处需要修正：

1. 不是「空响应」—— 是 **HTTP 500 + 26 字节文本 `500 Internal Server Error\n`**
   （Go `http.Error` 的标志性输出，来自 smart-git）。
2. 「git fetch 的 POST 全坏」**不成立** —— 真实 git（v0 协议）的 POST 完全正常
   （实测返回 200 + 4.6MB pack）。**只有 Git 协议 v2 格式的 POST 会 500**，
   而真实 git 客户端会自动回退 v0，**永远不会发出 v2 body**。

**根源：`wjqserver/smart-git` 不支持 Git smart-HTTP 协议 v2 的 POST 命令。**

## 故障链（实测验证）

```
git/工具 → DNS: github.com → 192.168.0.18（劫持，设计如此）
        → tengine :443 → v3-gitproxy（smart-git, Go, 127.0.0.1:8080）
        → POST git-upload-pack 的 body 是 v2 格式（command=...）
        → smart-git 不认识 → http.Error(w, "500 Internal Server Error", 500)
        → 响应体 = "500 Internal Server Error\n"（text/plain, 26B）
        → 客户端按 pkt-line 协议解析：读前 4 字节 "500 "
        → 第 4 字节是空格（0x20），不是合法十六进制
        → protocol error: bad line length character: 500
           （中文版：「协议错误：错误的行长度字符：500 」）
```

**「500」三个字符不是 HTTP 状态码的显示，而是响应体文本的前三个字符。**
这个巧合让报错极具误导性 —— 看着像 HTTP 层错误，实际是协议解析错误。

## 实验矩阵（全部实测于 2026-10-08）

| 请求 | 走缓存（.18） | 直连 GitHub 真实 IP |
|---|---|---|
| GET info/refs（v0/v2 header 均可） | ✅ 200 + 1737B 广告 | ✅ 200 |
| POST v0 协议（want/have，git 默认） | ✅ **200 + 4.6MB pack** | ✅ 200 |
| POST v2 ls-refs（`command=ls-refs`） | ❌ **500 + "500 Internal Server Error\n"** | ✅ 200 |
| POST v2 fetch（`command=fetch`） | ❌ **500 + 同上** | ✅ 200 |
| 真实 `git -c protocol.version=2 clone` | ✅ **成功**（自动回退 v0） | ✅ |

v2 的 500 是**稳定的**（3/3 复现），非间歇。

## 为什么真实 git 客户端不会中招

Git 协议 v2 是**协商制**：客户端在 GET info/refs 里带 `Git-Protocol: version=2`
试探，服务器应答里**没有** `Git-Protocol: version=2` 标识就自动回退 v0。
smart-git 的应答恰好没有这个标识 → git 回退 v0 → 一切正常。

**会中招的是**：固定发 v2 body 的非 C git 实现 —— go-git、libgit2 的某些封装、
自研 CI 拉代码工具等。它们的 POST body 以 `command=` 开头，
smart-git 一律 500。

## 生产现状（tengine git.log，近两周）

**当前没有正在发生的真实 git 500。** 全部 500 记录共 6 条：

```
4 × 192.168.0.19  POST TProxy.git/git-upload-pack   ← 本次分析我自己的测试
1 × 192.168.0.14  HEAD log-ui.git（9/24，历史）
1 × 127.0.0.1     GET git.git（9/23，历史测试残留）
```

`.70`/`.71` 每 2~4 分钟拉 `grigs28/ai_ops`（私有仓库），流程健康：

```
GET（无凭据）→ smart-git 透传上游 401 → git 带凭据重试
→ tengine 看到有 Authorization → 分流直连 github.com → 200
```

（smart-git 日志里反复出现的 `克隆 ai_ops 失败: 401` 是这个流程的回源侧，
属预期行为 —— 每次匿名首发都会触发一次注定失败的克隆尝试，有点浪费但无害。）

## 当时用户是如何撞上 500 的（推断）

实测排除了「真实 git 客户端 + 当前状态」后，剩下的触发窗口：

1. **拉代码工具不是 C git**：固定发 v2 协议 body（最常见，本报告实测可稳定复现）
2. **缓存过期 + 回源失败的窗口期**：`expire=30m` 到期后首个请求触发同步，
   上游超时/失败时 smart-git 返回 500
3. **私有仓库无凭据**且客户端不支持 401 重试

## 结论

- **机制确认**：劫持链路上 POST 返回的 `500 Internal Server Error\n` 文本
  被 pkt-line 解析器当长度前缀 → 报出含「500」的行长度错误。**用户假设的核心正确。**
- **范围收窄**：不是「POST 全坏」，真实 git fetch/clone 当前完全正常；
  只有 v2 协议 POST（真实 git 不会发）稳定 500。
- **根源在 smart-git 上游**（`wjqserver/smart-git` 不支持协议 v2 POST），
  不在 tengine 配置（`proxy_http_version 1.1` 等历史坑位**复查均在、未复发**）。
- 按用户要求：**未修改**任何配置与程序。

  -H "Content-Type: application/x-git-upload-pack-request" \
