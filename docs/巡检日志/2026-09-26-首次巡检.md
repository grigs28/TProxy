## 二、🔴 发现 P0：`deb.debian.org` 的劫持已失效，客户端直连公网

### 现象

```
$ dig @127.0.0.1 deb.debian.org A
deb.debian.org.           1084 IN CNAME debian.map.fastlydns.net.
debian.map.fastlydns.net.  292 IN A     151.101.66.132      ← 真实公网 IP
```

dnsmasq 日志：

```
query[A] deb.debian.org from 127.0.0.1
cached  deb.debian.org is <CNAME>              ← 不是 config …… is 192.168.0.18
cached  debian.map.fastlydns.net is 151.101.66.132
```

**该域名有 16 台机器在使用，它们的 apt 流量全部绕过 `.18`。**

### 根因

`address=/域名/IP` **只提供 A 记录**。当客户端查询 **AAAA** 时（glibc 的
`getaddrinfo` 默认 A 与 AAAA 并行发送，所以这几乎必然发生）：

1. dnsmasq 无 AAAA 可答 → **向上游转发**
2. 上游返回该域名的真实记录是一条 **CNAME**
3. CNAME 被写进 dnsmasq 缓存 —— 而 CNAME 是**类型无关**的
4. 此后 **A 查询也命中这条 CNAME**，链式追到真实公网 IP → 劫持失效

即：**凡是真实存在 CNAME 的劫持域名，都可能被一次 AAAA 查询打穿。**
这与既有记忆 `dnsmasq-hijack-traps` 里的「缓存压过 address=」是**同一个坑的新触发路径**，
区别是这次**不需要重启**，运行中自行发生、且 TTL 到期前反复被刷新。

### 影响面

普查 44 个劫持域名的现状：**目前只有 `deb.debian.org` 已击穿**，其余 43 个仍正常。
但其中 **约 16 个本身是 CNAME**，属同一脆弱性：

```
cn.archive.ubuntu.com  developer.download.nvidia.com  dl-cdn.openeuler.openatom.cn
download.proxmox.com   files.pythonhosted.org         gitee.com
maven.aliyun.com       mcr.microsoft.com              mirrors.aliyun.com
mirrors.cloud.tencent.com  mirrors.fedoraproject.org mirrors.tuna.tsinghua.edu.cn
pypi.tuna.tsinghua.edu.cn  registry.npmmirror.com     repo1.maven.org
repo.maven.apache.org
```

对照组（非 CNAME，AAAA 返回 NODATA-IPv6，**不受影响**）：
`security.debian.org`、`archive.ubuntu.com`、`ports.ubuntu.com`、`quay.io` 等。

### 佐证：有人在直接查 CNAME 目标

`debian.map.fastlydns.net` 被 **6 台机器直接查询** 134 次：

```
56 × .147   36 × .146   24 × .91   8 × .98   6 × .144   4 × .143
```

即客户端拿到 CNAME 后在自行追链 —— 这是绕过路径的独立佐证。

### 已排除的假设

- **IPv6 绕过**：实测 11 个域名经 `.18` 查 AAAA **均不返回 IPv6 地址**，此路不通。
- **AAAA 全线泄漏**：`security.debian.org` 等非 CNAME 域名 AAAA 返回
  `NODATA-IPv6`，干净。

## 七、P1 的前提被推翻（我先前判断不准，特此更正）

先前报「`repo.openeuler.openatom.cn` 漏在劫持清单外、240 次查询从不缓存」——
**技术上没错，但掩盖了它根本不承载数据这个事实**。实测：

```
302 → location: https://dl-cdn.openeuler.openatom.cn/...
      └─ 这个域名在 44 个劫持清单里，证书已签、tengine 已服务 ✅
```

它只是个 **302 跳板**，真正的负载（repomd.xml 等）**早就在走缓存**。
剩下没被缓存的只有每次 151 字节的跳转 —— **劫持它的带宽收益接近于零**。

唯一说得通的理由：对**不能直连公网**的客户端，这一跳会失败，劫持后可保底。
但那 4 台（`.112/.114/.115/.116`）显然能连（240 次查询一直成功），故收益仍很小。

**结论：不建议做**，除非用户要那点保底。已请用户裁示。

## 八、附带查清：`.91/.92/.143/.144` 的 pin 屡删屡回的元凶

用户提示看 `/mnt/79-sxiad/grigs/ve/ve.hosts.sh` —— 顺着查到了真正的源头：

| 文件 | 情况 |
|---|---|
| `/mnt/79-sxiad/grigs/ve/ve.hosts.sh` | `cat > /etc/hosts` 整份覆盖；github pin 段**已被注释**（9/25 13:56） |
| **`/mnt/79-sxiad/grigs/startup.sh`** | **元凶**。机器初始化脚本，含 `add_config "20.205.243.166 github.com" "/etc/hosts"` 等 7 条 |

关键在 `add_config` 的语义是「**没有就追加**」（`grep -qF ... || echo >> ...`）——
**所以每次 `startup.sh` 一跑，pin 就回来了**。这也解释了为何 4 台的 pin
**内容逐字相同**：同一个脚本、同一份输入。

它从 `http://192.168.0.29:8090/sxiad/grigs/` 拉 `bas.sh`/`up.sh` 自更新，
并配置 SSH / `rc.local` / rc-local service。

**处置**：该文件在 NFS 分发目录、**不归本项目管**（用户既定），
**未做任何修改**。只需把 `startup.sh` 里那 7 行按 `ve.hosts.sh` 的样子
注释掉即可 —— **交由其维护者处理**。

⚠️ 这同时说明：`tp.client.sh -i` 摘 pin 与 `startup.sh` 加 pin 是**拉锯**。
只要 `startup.sh` 还在跑，摘了就会回来。**根治点在 `startup.sh`，不在客户端脚本。**

### 🔴 顺带查出一个潜伏的定时炸弹：`ca/domains.txt` 缺 7 个域名

交叉核对四个权威清单时发现（详见 `CHANGELOG.md` 0.5.7）：

`deploy.sh` 是靠**遍历 `ca/domains.txt`** 签发证书的，而该文件**缺了 7 个劫持域名**
（正是 0.5.5 新增的那批）。`.18` 上证书目前齐全所以**暂时没事**，
但**只要 CA 重建一次**，这 7 个域名就没证书 → **Debian / Proxmox / GitHub-CLI /
nvidia 源的 HTTPS 全线断**。

**为什么常规巡检发现不了**：证书长期有效、CA 重建极少发生 ——
漏一个可能几个月都不出事，直到某次重建才集体爆掉。属「**已埋雷但未引爆**」。

**已修**（37 → 44）并加了「三件套齐全」守卫（劫持／服务／证书）。
负例已验证能拦住。
