# Git 缓存方案对比 · 实测证据 · smart-git 试验

日期：2026-09-24 ｜ 状态：**只记录与试验，未替换生产组件**

## 一、为什么查这个

`.14` 拉不到新代码。另一位 AI 归因为「`.18` 上的 Gitea 镜像停在 v0.5.1」。
**实际不是** —— `.18` 上跑的是 `tproxy/gitcache:local`（`gitcache -b /var/gitcache -p 4999`），
**没有 Gitea**。下面是实测出来的真实原因。

## 二、根因（三层，全部有实证）

### ① `gitcache` 缓存一次后**永不刷新**

官方 README：缓存不存在时重定向到 github.com 并**异步**建镜像；之后从本地镜像服务。
**没有 TTL / 刷新特性**，且明说"用 HTTPS `git remote update` 很难"。

实测（kubernetes）：

```
走缓存 HEAD = 30536385…     真 GitHub HEAD = bba12b9f…
缓存 mtime  = 2026-09-23 16:13:05     ← 两次请求纹丝不动
```

实测（log-ui，测量时顺手跑了一次 fetch）：

```
缓存 231bffa  →  上游 67c5832     ← 陈旧是常态，不是偶发
```

### ② git **不会**预先发 Authorization —— 最要命的一环

`GIT_CURL_VERBOSE` 实测：整个请求过程 `Authorization` 出现 **0 次**。
git 要等服务器回 **401 挑战**才发凭据。而 gitcache 对私有仓库返回的是：

```
GET /grigs28/sxbot.git/info/refs  →  200，**21 字节**（"Repository not found."）
GET /grigs28/sxbot.git/HEAD       →  404
```

**200 永远不会挑战 git** → git 不发凭据 → 永远走缓存 → 拿不到东西。
而 git 把空 ref 列表当成"空仓库、无变化" → **fetch 退出码 0、零输出、完全静默**。

### ③ 于是 tengine 那条「带凭据 → 直连上游」的分支**对 git 形同虚设**

`git.conf` 的 `map $http_authorization $git_has_auth` 逻辑本身是对的 ——
**强制加 `Authorization` 头就直连成功**（实测拿到 6 个 ref），但 **git 永远不发那个头**。

## 三、方案对比

| 软件 | 语言/依赖 | **刷新机制** | 私有仓库/凭据 | push | 状态 |
|---|---|---|---|---|---|
| **gitcache**（现用） | Go 单二进制 | ❌ **无**，首次建镜像后冻结 | ❌ 不校验；失败返 200 静默 | 靠 tengine 绕开 | 停更（2023） |
| **smart-git** | Go / Rust | ✅ **真 TTL**：Go `expire`+`expireEx`；Rust `refresh_ttl_secs` + 后台扫描 | ⚠️ 文档未提 | ⚠️ 未提 | 活跃 |
| **git-cache-proxy** | Rust | ✅ **每次服务前增量 fetch**（最新鲜） | ⚠️ 未提 | 只读（403） | 活跃 |
| **BlackGit** | Java 21+JGit+Netty | ⚠️ **无 TTL**；refs 首次惰性拉，blob 按需回源 | ✅ **必须带 Basic、原样转发上游** + 路径授权 | ✅ `w` 授权/文件锁 | 小项目 |
| **裸仓库镜像 + 定时 fetch** | 任意 | ✅ 定时（受间隔限制） | 需自配 | 全量副本 | 成熟但重 |

**三个痛点分别谁能治**：

| 痛点 | 谁能治 |
|---|---|
| ① 缓存永久冻结 | **smart-git**、git-cache-proxy、裸仓库+定时 |
| ② 私有仓库静默失败 | **BlackGit**（强制 Basic + 401 挑战，git 才会发凭据） |
| ③ push 直连 | 都不需要 —— tengine 已分流正确 |

**没有一个同时治好 ①②。**

## 四、成本实测（关键约束：翻墙流量要钱）

10 个缓存仓库，全量刷一遍的 ref 广告总量：

```
kubernetes/kubernetes      7,833,506   ← 独占 91%
git/git                      263,499
octocat/Hello-World          224,377
anthropics/skills            140,767
obra/superpowers             107,975
grigs28/TProxy                   784
grigs28/TAF-OpenEuler            234
grigs28/log-ui                   129
grigs28/PaddleOCR-ui              59
grigs28/claude-monitor            57
------------------------------------------
合计                       8,571,387 字节 ≈ 8.4 MB
```

**结论：成本几乎完全取决于「有没有巨型仓库」。**

| 对象 | 一次刷新 | 每小时刷，一个月 |
|---|---|---|
| 自己那批业务仓库 | **57 ~ 784 字节/个** | **< 1 MB** |
| kubernetes 这类巨型上游 | **7.8 MB** | 187 MB ← 这才贵 |

且缓存里那几个巨型仓库（kubernetes / git / octocat / anthropics / obra）
**是验证时顺手拉的，不是业务需要的** —— 本就不该占缓存、更不该刷。

## 五、smart-git 试验方案（可回退）

**目标**：在**不碰现有 gitcache** 的前提下，用同一批仓库对比新鲜度与私有仓库行为。

**做法**：在 `.18` 上以**独立容器 + 独立端口 4998** 起 smart-git（`.18` 的 DNS 是公网，
回源真 GitHub 不会被劫持；gitcache 仍在 4999 不动）。

**要验的三件事**（决定它能不能替代）：

1. **新鲜度** —— TTL 到点后，客户端拿到的 ref 是否等于真 GitHub
2. **私有仓库 + 凭据** —— 它文档完全没提，而这是 `.14` 的病根
3. **push** —— 是否被拒（`receive-pack`）；我们虽绕开，但要确认不会静默出错

**回退**：只需 `docker rm -f <测试容器>` —— 不触碰 gitcache、不改 dnsmasq、
不改 tengine、不改任何客户端配置。

## 六、若试验失败，退路（按性价比）

- **A. 定时刷新 + 白名单** —— 只对业务仓库 `git remote update`，成本 < 1 MB/月
- **B. 按需刷新**（git-cache-proxy 模型）—— 只有被真的拉取才回源，最省钱
- **C. 让 gitcache 失败可见** —— 它把"克隆失败"包成 `200 + Repository not found.`，
  git 于是静默。让它返 401/404，git 就会报错、也会触发 401 → 凭据发出 → 直连分支生效

## 七、试验结果（2026-09-24，`.18` 上端口 4998）

### Rust 版（`wjqserver/smart-git-rs:latest`）—— ❌ 镜像拉取失败

```
ERROR git mirror operation failed error=failed to fetch initial mirror from https://github.com/grigs28/log-ui.git
```

排除了以下可能：容器有 CA 证书、容器内 `wget https://github.com` **成功（563k）**、
DNS 解析正常、`<url>` 形态已修正（它自己会补 `.git`，写成 `log-ui.git` 会变成 `log-ui.git.git`）。
容器是 musl/Alpine、二进制静态链接、用 Gix（纯 Rust，`ldd` 无 libgit2）。
`RUST_LOG=debug` 也**不给**更细的错误。**结论：这个镜像的 Rust 版在本环境不可用。**

### Go 版（`wjqserver/smart-git:latest`）—— ✅ 可用

配置挂在 `/data/smart-git/config/config.toml`（注意不是 `config.wanf`）：

```toml
[cache]
expire   = "30s"     # 试验用，故意调短
expireEx = "10s"
```

日志显示它**真的从上游拉了镜像**（`Enumerating objects: 301` … `Total 301`），
`info/refs → 200 (341 字节)`，`/healthz → 200`。

### 三方 HEAD 对比（决定性的那一组）

| 来源 | TProxy HEAD | |
|---|---|---|
| 本地 `.19` | `0f421a88…` | |
| **真 GitHub**（`gitcache` 之外，`.18` 直连） | **`0f421a88…`** | ✅ 最新 |
| **gitcache**（现用 `:4999`） | **`76829594…`** | ❌ **旧，落后一个提交** |
| **smart-git**（试验 `:4998`） | **`0f421a88…`** | ✅ **与真 GitHub 一致** |

**这就现场复现了「拉到旧代码」** —— 同一时刻，gitcache 给的是旧提交，
smart-git 给的是真 GitHub 的提交。

### smart-git 的缓存记录（`/api/db/data`）

```
name = "TProxy"
head_oid   = "0f421a883d42c33e1a5ab85888e0947e769630d7"
status     = "synced"
expires_at = "2026-09-24T10:51:16Z"      ← TTL 机制确实在工作
```

### 回退方式

```bash
docker rm -f smart-git-test        # 只删这一个容器
rm -rf /opt/smart-git-go           # 可选，删数据
```

**不触碰**：gitcache（仍在 4999）、dnsmasq、tengine、任何客户端配置。

### 端到端验证：TTL 到点后是否真的跟上（决定性）

推一个新提交 `867f384` 到 GitHub，然后等 TTL（试验设为 30s）到点：

| 来源 | TProxy HEAD | |
|---|---|---|
| 真 GitHub（`.18` 直连） | `867f3849…` | 基准 |
| **smart-git**（`:4998`） | **`867f3849…`** | ✅ **自动跟上了新提交** |
| **gitcache**（`:4999`） | **`76829594…`** | ❌ **仍停在旧值** |

smart-git 的 db 记录印证了刷新的发生：

```
head_oid   = "867f38496fbae9ba514dd07bc6ec419569b0edd5"
status     = "synced"
updated_at = "2026-09-24T10:56:22Z"     ← TTL 到点后重新拉取的时刻
```

**同一时刻、同一个仓库：gitcache 给旧提交，smart-git 给真 GitHub 的提交。**
这就是 `.14`「拉不到新代码」的根因被消除的直接证据。

### 结论

| 项 | 结果 |
|---|---|
| Go 版能不能替代 gitcache | ✅ **能** —— 新鲜度、TTL、HTTP 接口全部验证通过 |
| Rust 版 | ❌ 本环境镜像拉取失败，暂不可用 |
| **私有仓库 + 凭据**（`.14` 的病根） | ⏳ **尚未测** —— 文档完全没提，需单独验 |
| **push** | ⏳ 尚未测 |
| 回退 | `docker rm -f smart-git-test` —— 零影响 |
