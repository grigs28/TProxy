# 真机巡检与客户端需求分析

日期：2026-09-24
目的：摸清全网机器的真实形态，归纳出 `tp.client.sh` **必须能自动处理**的情况。

## 一、怎么查的

- 扫 `192.168.0.0/24` 的 22 端口 → **66 台**开放
- 用 `root` + 口令登录，**成功 44 台**，失败 22 台（网络设备/NAS/超融合）跳过
- **禁区 23 台只读**：`.21 .22 .29 .30 .70 .71 .80-.84 .91-.99 .140-.142`
- 每台采集 20 项：系统 / 包管理器 / DNS / systemd-resolved / hosts pin /
  CA（系统·docker·java）/ 是否跑过 / apt（死源·重复·企业源·codename）/
  dnf（metalink·冗余段）/ git 重定向 / docker（mirrors·data-root·runtimes）/ 到 .18 的 443

## 二、形态分布（44 台）

| 维度 | 分布 |
|---|---|
| 系统 | openEuler 24.03（多 SP）、openEuler 25.03、Debian 12/13、CentOS 7、Ubuntu 24.04、istoreos |
| 包管理器 | dnf / yum（CentOS 7）/ apt |
| 分发平台 | 41 台有 `/opt/grigs/bas.sh`；**3 台没有**（`.9` `.17` `.78`）——已补建 |
| `dig` | 上述 3 台**都没有**，其余有 |
| `python3` | `.9` `.17` 没有（docker 的 JSON 处理依赖它） |
| DNS 指向 | `.18` 13 台 · `.48` 16 台 · 公网各种（`.68`/`.5.5`/`.29`/`8.8.8.8`…） |

## 三、接入状态四档

| 档 | 含义 | 机器 |
|---|---|---|
| ① 全新未接入 | DNS 公网、无 CA | 多数 |
| ② **半接入** | DNS 已指 `.18`、**CA 未装** → 劫持生效但 TLS 全断 | **`.16`** |
| ③ 已接入有残留 | DNS `.18` + CA 已装 + 还有 pin | `.91` `.114` `.115` `.116` `.143` `.144` |
| ④ 已接入且干净 | — | `.8` `.19` `.71` `.100/.112` `.113` |

**② 比①更糟**：`.16` 上 `curl https://repo.openeuler.org/` 直接
`SSL certificate problem: unable to get local issuer certificate`（curl 60），
http 也是 000。这台机器**现在用不了**。

## 四、需求（按危害排序）

### P0 —— 会把机器弄坏 / 不可逆

| # | 需求 | 现状 |
|---|---|---|
| R1 | **半接入态必须报成「错误」**，且给出"机器当前不可用"的结论 | 只把 CA 未装当普通 warning，从不说破组合含义 |
| R2 | **`repair_dnf_repos` 不得改写备份文件** | 已复现：`/etc/yum.repos.d/backup/*.repo` 里 baseurl 未注释时，`metalink=` 行**被删掉** |
| R3 | dnf 检查**不得递归**进 `backup/` 等 dnf 不读的目录 | `dnf_metalink_sources` 用 `grep -r`，把 `.9` 的两份备份报成问题 |

### P1 —— 没有平台时脚本不可用

| # | 需求 | 现状 |
|---|---|---|
| R4 | 兜底块要定义 `print_color` | **缺**，无 bas.sh 时第 1653 行 `print_color: 未找到命令` |
| R5 | 兜底 `print_*` 要支持 printf 语义 | **不支持**，`print_info "... %s" "$x"` 输出字面 `%s`，数字全丢 |
| R6 | 无 `bas.sh` 时不得提示 `ins_dnf` | 提示"可 `ins_dnf bind-utils` 后重跑"，而那个函数不存在 |

### P2 —— 缓存静默失效

| # | 需求 | 现状 |
|---|---|---|
| R7 | `HIJACK_DOMAINS` 与服务端 `dnsmasq.conf` 对齐 | 客户端 **10** 个 vs 服务端 **37** 个 → hosts 漏检 27 个（含 `quay.io`/`ghcr.io`/`mirrors.*`） |
| R8 | metalink 检查要排除 `enabled=0` 的段 | 全段禁用的 repo 也被报，dnf 根本不会读它 |

### P3 —— 环境差异要降级而不是崩

| # | 需求 | 现状 |
|---|---|---|
| R9 | 无 `dig` 时用 `getent hosts` / `nslookup` 兜底自检 | 直接**跳过整个 DNS 自检**；而这三台都有 `getent` 或 `nslookup` |
| R10 | 无 `python3` 时明确报「无法处理 daemon.json」 | 静默失败，用户以为处理过了 |
| R11 | `systemd-resolved` 活跃时 `--status` 要**告警**（它并行查询会破坏劫持） | 只打印一行"DNS 机制: systemd-resolved"，不说不利后果 |

### P4 —— 网络环境（要在文档/提示里体现）

| # | 需求 | 现状 |
|---|---|---|
| R12 | `192.168.0.48` 把 `github.com` 答成 `127.0.0.1`、`registry-1.docker.io` 答成 Meta 的 IP（`31.13.71.19`） | 无从得知。**指着 `.48` 的机器 github 根本不能用**，那些 `github.com→20.205.243.166` 的 pin 是绕它的补丁 |

## 五、验证方式

| 目的 | 用哪台 |
|---|---|
| 验"改动没弄坏现状" | **`.143` `.144`**（指定的验证机） |
| 验"摘除范围"（R7 的风险点） | 必须挑**有 pin 的**机器 —— `.143/.144` 的 pin 已摘干净，验不出来 |

### 巡检之外新发现并修掉的

- **死 Nexus 路径只认 `debian-proxy` 一条** → `.16` 的 `dnf makecache` 一直
  `Curl error (7)` 而脚本报「正常」。0.4.4 修，判据改为「内网 IP + `/repository/`」
- **修复判据漏了新检测项** —— 报问题、却说正常、修复没跑。**本项目第三次犯**
  （apt 漏「重复」、dnf 漏「metalink」、这次漏「死 Nexus」）。已加回归守卫
- **`set -u` 开在 `source bas.sh` 之前** → `.17` 无输出、退出码 1。0.4.5 修
